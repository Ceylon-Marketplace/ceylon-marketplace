# API.md

All endpoints are Next.js Route Handlers under `src/app/api/`, served from the same process as the app (see `docs/ARCHITECTURE.md` — there is no separate API server despite `.env.example` implying one). This list was generated by reading the actual exported HTTP method handlers in each `route.ts` file, not from the README, and corrected against it where they disagreed.

Auth convention throughout: `Authorization: Bearer <accessToken>`, checked per-route via `requireAuth`/`requireRole` from `src/lib/auth.ts` (see `docs/ARCHITECTURE.md` for why this isn't enforced by middleware).

## Listings

| Method | Path | Notes |
| --- | --- | --- |
| GET | `/api/listings` | Public. Filters: `keyword`, `categoryId`, `sellerId`, `location`, `condition`, `listingType`, `minPrice`/`maxPrice`, `sortBy`; paginated (`page`, `limit`, capped at 100); `Cache-Control: s-maxage=30, stale-while-revalidate=60` |
| POST | `/api/listings` | Requires `SELLER`/`BUSINESS_SELLER` role. Enforces: no duplicate title (case-insensitive) among the seller's non-archived/sold listings, max 10 media items, at least 1 media item required |
| GET / PATCH / DELETE | `/api/listings/[id]` | |
| GET | `/api/listings/mine` | Own listings |
| GET | `/api/listings/saved` | Own saved listings, newest first, with listing media and category; excludes unused seller profile data |
| POST / DELETE | `/api/listings/[id]/save` | Save/unsave |
| POST | `/api/listings/upload-image` | Uploads to Supabase Storage |
| DELETE | `/api/listings/delete-image` | |

**Verified gaps vs. the README's stated business rules** — don't assume these are enforced server-side just because the README says so:

- **Title length (10–120 chars):** enforced client-side only, in `listings/create/page.tsx` and `listings/[id]/edit/page.tsx`. The `POST /api/listings` handler does **not** re-validate this — a direct API call can bypass it.
- **Max 3 videos:** no such limit exists anywhere in the codebase (only "max 10 media items total" is enforced, undifferentiated by type). Either the README is wrong or this was never implemented — flag before relying on it.
- **Expired subscription blocks new listing creation:** no subscription check exists in `POST /api/listings`. A user with an `EXPIRED` subscription is not currently prevented from creating a listing at the API layer.

If you touch listing creation, this is a good opportunity to either implement these checks server-side or correct the README — don't leave a third session finding the same gap.

## Error handling convention

Every handler wraps its body in `try { ... } catch (err) { return handleError(err); }` (`src/lib/auth.ts`). `ApiError` carries an explicit status code; anything else becomes a generic 500 with the error logged server-side via `console.error`. Follow this convention for new routes rather than hand-rolling error responses.
